# Order Management System — Capstone Requirements

Source: a 5-part capstone activity to build an **Order Management System** that manages inventory items and customer orders across multiple fulfillment centers. Each part builds on the previous; the project must compile and run at every checkpoint.

---

## Part 1 — Data model and persistence

### Project setup

- Create an ASP.NET Core Web API project (`dotnet new webapi`).
- Add a `Models/` folder containing `InventoryItem.cs` and `Order.cs`.

### `InventoryItem` model

- Properties:
  - `ItemId` (int)
  - `Name` (string)
  - `Quantity` (int)
  - `Location` (string)
- `DisplayInfo()` method that prints in the format: `Item: Pallet Jack | Quantity: 12 | Location: Warehouse A`.
- A sample object must be testable from `Program.cs` or a test controller.

### `Order` model

- Properties:
  - `OrderId` (int)
  - `CustomerName` (string)
  - `DatePlaced` (DateTime)
  - A list of `InventoryItem`s representing the items in the order.
- Methods:
  - `AddItem(InventoryItem item)`
  - `RemoveItem(int itemId)`
  - `GetOrderSummary()` returning a string like: `Order #1001 for Samir | Items: 2 | Placed: 4/5/2025`
- Must be testable: create an order, add/remove items, and print the summary.

### EF Core persistence

- Add the `Microsoft.EntityFrameworkCore.Tools` package.
- Create an `AppDbContext` (EF Core `DbContext`).
- Annotate model properties with `[Key]`, `[Required]`, and `[ForeignKey]` as needed.
- Generate and apply the initial schema:
  - `dotnet ef migrations add InitialCreate`
  - `dotnet ef database update`

### Seed and verify

- Add test data confirming that the DbContext is working, the inventory table is populated, and `DisplayInfo()` works correctly against persisted data.

### AI-assisted review (Copilot)

- One-to-many relationship between `Order` and `InventoryItem` should be modeled correctly in EF Core.
- Order summary printing should be efficient.
- `AddItem` should be reviewed for performance.
- Apply refactors as suggested; ensure everything compiles and runs with no errors.

## Part 2 — Web API endpoints

### Project structure

- Add `Controllers/InventoryController.cs` and `Controllers/OrderController.cs`.
- Use dependency injection to obtain `AppDbContext`.

### Inventory endpoints

- `GET    /api/inventory`       — return a list of all inventory items.
- `POST   /api/inventory`       — add a new item.
- `DELETE /api/inventory/{id}`  — remove an item by id.

### Order endpoints

- `GET    /api/orders`          — return a list of all orders.
- `GET    /api/orders/{id}`     — return an order with its items.
- `POST   /api/orders`          — create a new order; the payload must accept multiple inventory items.
- `DELETE /api/orders/{id}`     — delete an order by id.

### Acceptance criteria

- Endpoints must be testable via Swagger (auto-generated by ASP.NET Core) or Postman.
- Inventory items and orders can be created, read, and deleted via the API.
- Data persists in the database between requests.

### AI-assisted improvements (Copilot)

- `GET /api/orders/{id}` should include nested item details.
- Missing-id requests should return appropriate error responses.
- Controllers should use `async` methods throughout.

## Part 3 — Authentication and authorization

### Identity setup

- Install:
  - `Microsoft.AspNetCore.Identity.EntityFrameworkCore`
  - `Microsoft.EntityFrameworkCore.Sqlite`
- Create an `ApplicationUser` class that inherits from `IdentityUser`.
- Make `AppDbContext` inherit from `IdentityDbContext<ApplicationUser>`.
- Register Identity in `Program.cs`:

  ```csharp
  builder.Services.AddIdentity<ApplicationUser, IdentityRole>()
      .AddEntityFrameworkStores<AppDbContext>();
  ```

- Generate and apply the migration:
  - `dotnet ef migrations add AddIdentity`
  - `dotnet ef database update`

### Auth endpoints

- `POST /api/auth/register` — register a new user.
- `POST /api/auth/login`    — authenticate and return a JWT.
- Use `UserManager` and `SignInManager` to perform identity operations.

### Authorization

- Protect endpoints in `OrderController` and `InventoryController` with `[Authorize]`.
- Assign an admin role (for example, `"Manager"`) and restrict specific routes with `[Authorize(Roles = "Manager")]`.

### Acceptance criteria

- A user can register, log in, receive a JWT, and access protected routes only when authenticated.
- Role-restricted routes are rejected for users without the required role.

### AI-assisted review (Copilot)

- Verify that JWT authentication is configured correctly.
- Confirm role-restricted route protection works as expected.
- Review user-registration code for security weaknesses.

## Part 4 — Caching and performance

### In-memory caching

- Register the in-memory cache in `Program.cs`: `builder.Services.AddMemoryCache();`
- Inject `IMemoryCache` into the controllers that need it (starting with `InventoryController`).

### Cache the inventory list

- `GET /api/inventory` must:
  - Store the inventory query result in memory for 30 seconds.
  - Return the cached value on subsequent requests within the TTL.
- Cached routes must still return valid data and refresh appropriately when the TTL expires.

### Query optimization

- Use `.Include(...)` to eager-load related entities and avoid N+1 problems.
- Use `.AsNoTracking()` on read-only queries.
- Refactor slow or repetitive queries in `OrderController`.

### Measurement

- Compare performance before and after caching using `Stopwatch` or a profiler.

### AI-assisted review (Copilot)

- Surface controller-level performance improvements.
- Identify and eliminate repeated database calls for the same result.
- Apply Copilot suggestions and re-test.

## Part 5 — State persistence and final review

### Persistence strategy (choose one)

- **Caching strategy** — use `IMemoryCache` with longer expiration and rehydration logic.
- **Database strategy** — confirm that critical state survives server restarts by verifying database persistence.
- For cart-like or temporary order data, consider storing session IDs or user tokens as part of the order model.

### Full-system validation

Test the complete workflow end-to-end:

- Inventory and order creation.
- Authentication and access control.
- API response times and cache behavior.
- Error handling for invalid input.
- Secure access to role-restricted routes.

Use Swagger or Postman to simulate realistic usage.

### Final review (Copilot)

- Remove redundant logic.
- Apply final performance improvements.
- Address any remaining gaps relative to a "production-ready API" checklist.

### Deliverable

A complete, portfolio-ready API system ready for peer submission and review.
